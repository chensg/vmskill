# 画面：静帧、视频镜、素材分辨率

> 2026-09-25 从 SKILL.md 拆出来，正文原样搬过来（只改了指向别处的那几句）。

## 静帧模式：不做运镜的时候

`MOTION = "static"`，一镜一张不动的画。逐镜可覆盖：`dict(..., motion="static")`，
所以"整片静帧"和"只有尾板静帧"是同一个开关的两种用法。

**什么时候选它**：图本身信息量大、值得停着看（长卷、地图、老照片、信息图）；
素材分辨率不够做运镜；片子有强的语音在带节奏（讲述片尤其）；
或者就是要那个"一页一页翻"的调子。

### 声明要显式，不能靠"z 起止写成一样"

静帧和运镜在参数上只差"起止一不一样"，所以看起来把 `z=(1.2,1.2)`、`f0==f1`
写下去就够了。**不行**：这条流水线最贵的那个 bug——写了位移却没给足缩放、
成片变成原地微缩放——长出来的样子正是"起止实际上一样"。
如果允许隐式，那个 bug 从此变成一个合法配置，`check_moves` 再也拦不住它。

所以两边都拦，而且不去猜哪个是真的：

- 标了 `static` 却写了行程 → 报错
- 标了 `kenburns` 却起止完全一样 → 报错（**这正是那个 bug 的样子**）
- `motion` 写错字 → 报错

### `motion` 命令反过来判静帧镜

渲完跑 `motion`，它量每镜首尾帧的平均绝对差：

| | 判据 | 实测（testsrc2 两镜） |
|---|---|---|
| 运镜镜 | 均差 **≥ 4.0** 级 | 37.7 |
| 静帧镜 | 均差 **≤ 0.6** 级 | 0.1 |

**"静帧镜其实在动"和"运镜镜其实不动"一样是错**，而且更隐蔽——
静帧片里混进一镜缓慢的推近，看片时只会觉得"这一段怪怪的"。
如果只判运镜那一边，静帧片跑 `motion` 会全绿，那又是一个不会报警的检查。
（两个方向都拿故意标反的配置回归验过。）

### 连带改的三件事

**一、素材分辨率门槛从 pp 1.20 降到 1.00。** 这是静帧模式最实际的收益。

运镜镜要 1.20 的余量，是因为 `zoompan` 每一帧都在**非整数倍率**上重采样
（实测 pp=1.0 时只剩 92% 的顶层细节，1.20 才到 98%）。静帧镜没有这回事：
pp=1.0 时裁出来的窗**正好等于输出尺寸**，是恒等重采样，根本不过滤波器。

所以静帧镜要的源图短边就是 `z × 1080`——z=1 时**就是 1080**。
**这不是把检查放松了，是这一镜本来只需要这么多。** 而它决定了能不能用
博物馆开放数据里的画、档案馆的老照片——那些东西很多刚好卡在这条线附近。

**二、每镜停留要缩短，节奏全落在转场和声音上。**（**推测，还没有一支静帧片验过**）
运镜片每镜停 10~13s 是因为镜头一直在走；静帧片画面不动，同样的停留会显得更长。
起手可以试 6~9s，但仍受可读下限约束（每字 0.45s + 1.8s 起读，七言一句 4.95s）。
片长跟着缩，反过来让配乐余地更宽裕，那是好事。
转场时长这时**更不该是常数**——它是全片唯一的视觉节拍。

**三、粒子层从加分项变成全片唯一的真运动。** 雨、落叶、星辉那三种做法不变
（见 `poem.md`「粒子层」那一节），但在静帧片里它们的性价比高得多。

### `trace` 的落幅平坦度对静帧镜换了含义

平坦行原本在问"落幅停在这里会不会像静止"，而静帧镜本来就静止，那个问题不成立。
静帧镜只剩一个有意义的问题：**这张画停这么久够不够看**。
所以脚本对静帧镜只在整帧极差 < 25 时提示"会很空"，而且只是提示，不是判据。

## 视频镜：`CLIPS` 里给 `video=`，和静帧镜平级

历史题材有时**存在真的影像**（档案新闻片、早期电影残片、公版纪录片）。
图是「关于那件事的画面」，影像是「那件事本身」——有它而不用，
等于把最硬的证据换成了示意图。

```python
CLIPS = [dict(video="A.mp4", ss="20:10", to="20:30", tweak="")]
```

判据和静帧镜/运镜镜**都不一样**，五条：

| | 视频镜 | 为什么 |
|---|---|---|
| `pp` 分辨率 | **不判**，单列一张表只报事实 | 640×480 铺到 1080 是 2.25 倍放大，一刀切会把整支片子判死，而「糊」是这类素材的内容本身 |
| `motion` 首尾帧差 | **两个方向都不判** | 腐蚀严重的档案影像首尾差可能极小，那是内容不是「运镜看不出来」 |
| `check_moves` | 跳过 | 没有取景窗，`z`/`f` 对它没有意义 |
| `check_reuse` | 跳过（改由 `check_video` 查段重叠） | 同一影片取不同时间段本来就是两镜 |
| `check_video` | **新增，专judge 这一类** | 段够不够长、入出点在不在源片里、相邻同源镜有没有重叠 |

**时长永远由旁白说了算。** `to-ss` 是素材段，镜长是旁白算出来的，
两者没有约束关系。段短了 `pass_a` 会冻结末帧补足——画面僵住而退出码是 0。
所以 `check_video` 拦两级：短了拦，只多不到 `VIDEO_HEADROOM`（0.5s）也拦，
因为**旁白重新生成后镜长会变，现在刚好够等于以后不够**。

**`VIDEO_FIT` 默认 `"pillarbox"`（加黑边），不裁。** 4:3 裁 16:9 要丢 25% 的画面；
讲残缺、讲遗失、讲「还剩多少」的题材裁了就是画面在反驳旁白。

**帧率在 `prep` 就落到 `FPS`，但用丢/复帧，不要插值。** 不统一 concat 会时间戳乱
而且不报错；改成 `minterpolate` 则会把默片的抖动抹成糊的，
而抖动往往正是「这是老片子」的全部信号。

**授权和图走同一张 `CREDITS`，键是视频文件名**，`credits` 导出会多两列：
类型和**用到的段**。别把「能下载」当成「能再用」——底层作品和这一次
数字化/修复是两层权利，而把腐蚀修干净的那一版既可能有新权利、
也已经洗掉了你要讲的东西。

细节见 `references/storytelling.md` 第六节之补。

## 素材的分辨率是硬门槛

判据是 **pp = 源像素 / 输出像素**，按**每一镜自己的最紧取景**算：
`pp = 裁后有效短边 / 这一镜最大的 z / 1080`。

**旧版写的是"短边 ≥ 成片对应边的 1.5 倍"，那是个 flat 判据，两头都不对**：
对缓推镜多要一倍多的像素，对大推镜反而放行（4K 配 z=2.7 时 pp 只有 1.0 也能过）。

### 拐点是量出来的，而且和画面类型无关

两张**验过是真原生**的图库照片（一密一疏），同一个镜头走完整流水线，
量落幅帧的最高倍频程：

| pp | 0.70 | 0.85 | 1.00 | 1.20 | 1.30 | 1.45 |
|---|---|---|---|---|---|---|
| 保住的顶层细节 | 67% | 83% | 92% | 98% | 99% | 100% |

**两条曲线差不到两个百分点** —— 密和疏一样。所以尺寸只由**运动**决定；
画面类型改的是"最后那几个百分点值不值得买"，不改公式。

于是三档目标：

| | pp 目标 | 为什么 |
|---|---|---|
| 静帧镜 | **1.00** | pp=1.0 时裁出来正好等于输出尺寸，**恒等重采样**，不过滤波器 |
| 运镜镜 | **1.20** | 98%。zoompan 每帧在非整数倍率上重采样，所以要余量 |
| 细节镜 | **1.30** | 99%。人脸特写、工笔织物、市井细节、封面 |

判据分两级：**pp < 1.0 = 在放大，是缺陷，`check` 拦下**；
1.0 到目标之间是取舍不是缺陷，只提示。

### 上限是 PREP，不是钱包

`prep` 第一步就 `scale` 到 `PREP`（竖横版短边都是 2160）。
**源图短边超过 2160 的部分，在流水线第一步就被丢掉了**，后面所有环节都碰不到。
要 2896 等于交给流水线 2160，白付 26% 的线性分辨率、45% 的像素。

某一镜的 z 大到需要 > 2160 时，`budget` 会标出来：那不是素材问题，
是**流水线的天花板**——再大的源图也补不回来，要么降 z、要么改静帧、要么抬 PREP。

### 出图之前跑 `budget`

它按镜反推需要的尺寸并分档汇总，**出图任务书直接抄那张分档表**。
实测在两支已交付的片子上，按镜要比统一 2896 省 **60%~63%** 的像素。

低于 pp=1.0 的代价是**运镜没法做**：941×1672 那一张（当年下限的 0.65 倍），
那一镜的行程只能从 30% 压到 11%，几乎不能动；而这是一支每镜要停十秒半的片子，
镜头一旦不动，十秒会显得非常长。

AI 生成时**务必显式指定尺寸**——很多工具默认出 1K，9:16 的 1K 只有约 1024×1820，
在典型的 z≈1.45 下 pp 只有 0.65，实测只剩 **6 成**的顶层细节。这一条被坑过两次。
但**指定的那个数要来自 `budget`，不是一律填 4K**。

### 第三次：**文件尺寸会骗人**（《青玉案》）

生成器封顶在 941×1672，于是把图**放大**到 2896×5152 再进项目。
文件上写着 2896×5152，任何只看像素尺寸的检查从此必然通过，
而细节还是 941 那么多——有效值是下限的 **0.65 倍**，最紧那一镜每个输出像素
只摊到 **0.59 个源像素**，成片会软。

**试过从像素上自动判"是不是放大的"，判不出来**，两条路都不行：

- 把图降到**恰好**原生尺寸再放大回来，量残差：结果 0.23~0.57 灰阶，
  而原生 4K 是 0.53~0.83——**一个量级，分不开**。
  放大器不是简单重采样（AI 超分会造出细节）时尤其如此
- 1:1 目视对比也不可靠：两张图的"软"可能只是画风、题材或光线不同。
  拿雾夜灯市和硬光工坊比"锐不锐"，比不出东西

唯一站得住的证据是**生成器吐出来的原始文件**（去它的生成目录看尺寸）。

所以这一条**只能靠记录，不能靠检测**：脚本里的 `SRC_NATIVE` 写生成器实际出的尺寸，
`check_resolution()` 按它折算有效短边，而不是读文件。

配套的 `pixels` 命令从每张源图裁 1:1 原始像素贴片拼一张，让你看一眼——
它是辅助，不是判据，理由见上面第二条。**和 `still` 之于字幕是同一个套路：
自动判不出来的，就做成必须看一眼的东西。**
